# V32 Canary·즉시 Rollback 계획 (Phase 7)

작성 2026-08-18. 상태: **설계 확정, 운영 반영은 대표 승인 후** (운영 앱 수정 금지 원칙 준수 —
이 문서의 구현은 상용화 전환 승인 시점에 render-server에 적용한다).

## 1. Feature flag 구조

render-server(감시원)에 환경변수 3개를 추가한다. 코드 배포 없이 Railway 변수 변경만으로
동작이 바뀐다 (변경 반영 = 컨테이너 재시작 약 30~60초).

| 변수 | 값 | 의미 |
|---|---|---|
| `WM_PIPELINE_DEFAULT` | `v29`(기본) / `v32` | 신규 작업의 기본 파이프라인 |
| `WM_V32_CANARY_PCT` | `0`~`100` (기본 0) | 무작위 canary 비율(%) — project id 해시 기준 결정적 |
| `WM_V32_ALLOW_USERS` | 쉼표구분 user_id (기본 비움) | 지정 사용자만 강제 v32 (내부 테스트용) |

선택 로직: `ALLOW_USERS`에 있으면 v32 → 아니면 `hash(project_id) % 100 < CANARY_PCT`면 v32
→ 아니면 `DEFAULT`. 같은 프로젝트 재시도는 항상 같은 파이프라인(결정적 해시)이라
재현·비교가 가능하다.

## 2. 자동 안전장치 (canary 중 자동 강등)

- v32 작업이 **실패**하면 그 작업은 즉시 v29로 자동 재실행 (고객은 지연만 경험, 실패 없음).
- 최근 20건 중 v32 실패율 > 10% 또는 finish 검증 게이트(프레임/오디오/해상도) 불일치 발생 시:
  감시원이 `WM_V32_CANARY_PCT=0`으로 자체 강등하고 관리자 알림 (Slack/이메일).
- 저신뢰(fallback_needed) 판정 작업은 v32 결과를 버리고 v29 재실행 (Phase 2 게이트 재사용).

## 3. 즉시 Rollback 절차 (목표: 5분 이내)

1) Railway 대시보드 → render-server → Variables → `WM_V32_CANARY_PCT`를 `0`,
   `WM_PIPELINE_DEFAULT`를 `v29`로 변경 → 자동 재시작 (약 1분).
2) 진행 중이던 v32 작업: 완료 대기(무해) 또는 실패 시 v29 자동 재실행 경로로 흡수.
3) Modal v32 staging 앱은 그대로 두어도 비용 없음 (min_containers=0, 호출 없으면 0원).
4) 확인: 신규 작업 1건 제출 → wm_done.ver == "v29" 확인.

전제 조건(이미 충족): v29 운영 경로는 어떤 v32 변경에도 손대지 않았고, 태그
`wm-v29-production-baseline`으로 고정되어 있다. v32는 별도 Modal 앱·별도 임시 경로
(`wmtmp-v32/`)만 사용하므로 저장소 충돌이 없다.

## 4. 단계적 확대 계획 (승인 후)

| 단계 | CANARY_PCT | 조건 |
|---|---|---|
| C0 | 0 (내부 계정만) | 골든 10개 통과 + queue 10건 부하검사 통과 |
| C1 | 1% | C0에서 실패 0, 48시간 |
| C2 | 10% | C1에서 실패율 < 2%, 품질 민원 0, 72시간 |
| C3 | 50% → 100% | 대표 승인 (운영 1% 초과 전환은 사전 보고 원칙) |

C1 진입 자체가 "운영 1% 전환"에 해당하므로 **C1부터 대표 사전 승인 필요**.
