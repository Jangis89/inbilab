# warm/dedicated/hedge 통제실험 결과 (Phase 8, 2026-08-18)

원칙 준수: 모든 실험은 예열 호출 방식(min_containers/buffer_containers 미사용) —
컨테이너는 scaledown 300초 후 자동 소멸하므로 실험 종료 즉시 GPU 0 상태로 자동 원복.
RunPod workersMin=0 유지. 상시 GPU 활성화 없음.
공용 큐 구조: Modal 호출 큐 = 공용 segment queue(고정배정 없음) + 벤치 드라이버의
delayed hedge + first-valid-result-wins (구현·검증 완료, --hedge 인자).

## 판정
1. **warm3 가설 통과**: P50 169.8 ≤ warm12×1.10(178.9), P95(최대 180.1) ≤ 480.
   예열 GPU 12→3으로 줄여도 체감 차이 ~7초. 비용: 예열 GPU-초 75% 절감.
2. 콜드 페널티의 실체: 유휴 후 첫 작업 1건만 배정지연 2~3분. 이후 작업은 동일.
   시간대에 따라 변동 큼 (같은 날 10~195초 관측 — Modal 용량 상황 의존).
3. hedge120: 콜드 폭풍에서 11/12 세그 발사됐지만 승자 0 — 복제본도 같은 콜드 큐에
   갇히므로 콜드 폭풍 해결책은 아님. 진짜 용도는 '실행 지각'(1000초급 스트래글러) 보험.
   비용은 스트래글러 시에만 발생 → 운영 기본값 hedge=120 권장 (평시 비용 0).
4. 부수 발견·수정: 저장소 일시 지연(ReadTimeout 1회)이 finish를 통째로 죽이는 버그
   → 폴링 예외 방어로 수정 (커밋 완료).

## 운영 권장 (Phase 10 제안으로 연결)
- 평시: warm 3 (요청 직전 예열 or 짧은 유휴예열), hedge 120s, max_containers 32
- 대기열: FIFO 1-at-a-time + finish 겹침 (10건 부하검사 검증 완료)
- 상시(24h) GPU: 불필요 — 유휴 후 첫 고객만 +2~3분이며, 이는 ETA 안내로 흡수 가능.
  트래픽 증가로 유휴 구간이 사라지면 자연 해소. 대표 승인 전 상시 GPU 금지 유지.
