# RC3 사고 기록 (정직 고지)

## INC-1 (2026-08-20): UAT 복제 행을 운영 v29가 선점 처리

- **원인**: 내가(Claude) UAT-02 복제 행(beac0005-…51)을 손으로 만들며 상태값을
  `uploaded`로 넣음 → 운영 v29 워커가 신규 업로드로 인식해 처리함.
  검증된 안전 절차는 uat_run_v32.py가 복제를 직접 만들고 상태를 `wm_done`으로
  넣어(운영이 절대 집지 않는 값) staging만 pid를 지정 처리하는 방식이었다.
- **영향**: 운영 GPU 1회 소모(175초 영상 1건, 비용 추정 ≈ $0.7).
  운영 서비스 중단 없음 · 고객 데이터 무영향 · UAT 원본 3편 무변경(확인됨).
  같은 워크플로의 v32 staging 처리(run #118)는 안전 경로(@…01, wm_done 복제)로
  정상 수행되어 결과물 검증에는 지장 없음.
- **조치**:
  1. (즉시) 이후 모든 UAT 재처리는 uat_run_v32.py에 **원본 pid만** 전달 —
     복제 생성은 스크립트에게만 맡긴다. 손으로 `uploaded` 행 생성 금지.
  2. beac0005-…51 행·산출물은 정리 대상 목록(V32_UAT_TEST_DATA_CLEANUP_PLAN)에 추가.
  3. 이 기록을 RC3 매니페스트의 알려진 사건 항목으로 유지.
- **재발 방지 확인 방법**: 복제 행 생성 직후 status 값이 `wm_done`(스크립트 생성)인지
  확인. `uploaded` 상태의 beac0005-* 행이 존재하면 즉시 중단·보고.

## INC-2 (2026-08-20): 운영 자동 정리 기능이 UAT-02·03 원본 스토리지 파일 삭제

- **원인**: 서비스의 원본 정리 정책(완료 24시간 후 원본 소스 삭제 — cleaned_at)이
  원본 프로젝트(d5a9ae7f 11:43Z, 5ddc260c 11:53Z)의 소스 파일을 삭제.
  RC3 작업과 무관한 운영 설계 동작이며, UAT-01(bad96c77)은 전날 v29
  자동감지 실패(failed_wm, 8/19 11:25Z) 상태여서 정리 대상에서 제외돼 살아남음.
- **영향**: rc3-6·rc3-7 재처리에서 UAT-02·03 scan이 "원본 없음(400)"으로 실패.
  원본 '영상 내용'은 무손실 — 사고 전 확보한 SHA256 검증 사본 보유.
- **조치**: 같은 경로에 재업로드 후 바이트 수 정확 일치 검증
  (159,536,565 / 119,951,400 bytes ✓). 로컬·해시 기록 유지.
- **재발 주의**: 정리 잡이 다시 돌면 재삭제될 수 있음 — RC3 기간 중 로컬 사본
  유지, 매 UAT 전 서명 URL 사전 점검. 서비스 정책 자체의 조정 여부는 대표 판단
  사안(문서화만, 변경하지 않음).
